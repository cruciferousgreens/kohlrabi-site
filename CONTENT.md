# Kohlrabi marketing site — content guide

`getkohlrabi.com` is a small static site. Every page is plain text + markup; a
build script (`python3 build.py`) stitches it together. This guide tells you
where each piece lives and the rules that keep the site working.

## Where the words live

**Page copy lives in `src/pages/*.html`** — one file per page (e.g.
`src/pages/install.html`). Each file has two parts:

1. A small settings block at the top (page title, the 1–2 sentence
   description shown in search results, the canonical link).
2. The page's content between the markers — this becomes the inside of
   `<main>` on the finished page. No header/nav/footer boilerplate here;
   that's added automatically.

**Never edit the built pages at the repo root** (`index.html`,
`install.html`, …). Each one is stamped `<!-- Generated by build.py from
src/pages/<name> — edit the source, not this file. -->` and the next build
regenerates it from `src/pages/`, wiping any hand-edit.

**Example workouts and programs** are not in `src/pages/`. Their copy lives in
the data files under `assets/examples/` (one file per workout/program, plus a
`manifest.js` list). The finished detail pages (`/workouts/<slug>`,
`/programs/<slug>`) are built from those files, and they also feed the cards
on the examples page, the sitemap, and `llms.txt` — so a copy fix there shows
up in all four places after a rebuild.

## Navigation and footer

The menu bar exists in **two places that must match**: the build script
(`build.py`, `render_nav()`, which draws the menu at build time so it shows
instantly) and `assets/components.js` (`nav()`, a fallback for older cached
pages). If you ever change a menu link, change both copies and run
`python3 tools/check-nav-parity.py` from the repo root to confirm they match.

The footer has a single source of truth: the `footer()` function in
`assets/components.js`. The file `src/components/footer.html` is only an empty
slot the script fills in — it holds no footer content itself.

## The donate card rule

The "Keep it free." donate card (`<section class="donate-card">`) must sit
**inside the page's content column** (the `<section class="subpage">` or
equivalent wrapper), never placed directly under `<main>`. Outside the column
it stretches to the full width of the screen.

## Styles: the per-page CSS workflow

All styling starts in `assets/site.css`. The site ships a small per-page CSS
file (`assets/css/<page>.css`) so each page loads only the styles it uses.
Those per-page files are **generated — never hand-edit them**. After changing
`assets/site.css`:

1. Serve the built site locally (`python3 -m http.server …` — keep it running
   in its own session; it can die silently mid-run).
2. Temporarily point the built pages at `assets/site.css` (the coverage tool
   records the stylesheet URL, and built pages normally link the per-page
   files, so without this step it finds no data).
3. `node tools/css-coverage.mjs <url>` — records which CSS each page actually
   uses (writes `/tmp/css-coverage.json`). New pages must be added to the crawl
   list in `tools/css-coverage.mjs` or they get no CSS file (this is how
   `404.html` once shipped unstyled).
4. `python3 tools/split-css.py` — writes `assets/css/<page>.css`.
5. `python3 build.py` — restores the proper per-page links and regenerates the
   built pages. This final build wipes the temporary swap from step 2.

Selectors that depend on state (`:hover`, `:focus`, `.open`, …) are always kept
in every page's CSS.

## Search engines: sitemaps, robots, llms.txt

`python3 build.py` runs `tools/gen-sitemap.py` automatically. It writes:

- `sitemap.xml` (index) plus `sitemap-pages.xml`, `sitemap-workouts.xml`,
  `sitemap-programs.xml`
- `robots.txt` and `llms.txt` (a plain list of the site's pages for AI
  assistants, rebuilt from current titles)

The 15 sitemap page URLs are a fixed list in `tools/gen-sitemap.py`
(`PAGES =`). Left out on purpose: `beta` (it's marked `noindex`), the generic
`/program` and `/workout` resolver shells, and `preview-hero.html` (a draft).
The 66 example workouts and 8 programs are pulled from the
`assets/examples/` data files.

**`?v=` version numbers** on CSS/JS links bust the browser cache. The value is
the Cloudflare Pages deploy commit when Pages builds the site, the git commit
otherwise, or a timestamp as a last resort. Pages rebuilds (and re-stamps) on
every push to `main`.

## Front-matter knobs per page

The settings block at the top of each `src/pages/*.html` accepts:

- `title` — the browser-tab/search-result title
- `description` — the search-result snippet
- `canonical` — the one true URL (no `.html` in the nav links)
- `nav_page` — which menu item counts as active
- `css_page` — which per-page CSS file to load (defaults to the page name)
- `head_extra` — page-specific tags (e.g. workout JSON-LD)
- `head_raw` — replaces the whole `<head>` with your own markup (used by the
  `preview-hero` draft)
- `robots` — e.g. `noindex` for `beta` and `404`
- `examples_loader` / `examples_attrs` — mark pages that render
  example-workout data

## Quick recipes

- **Fix a typo:** edit `src/pages/<page>.html` (or the `assets/examples/`
  data file for a workout/program), run `python3 build.py`.
- **Add a page:** create `src/pages/<page>.html`, add it to the crawl list in
  `tools/css-coverage.mjs`, run the CSS workflow above, then `python3
  build.py`; add its URL to `PAGES` in `tools/gen-sitemap.py` if it should be
  indexed.
- **Change a style:** edit `assets/site.css`, run the full CSS workflow above.
